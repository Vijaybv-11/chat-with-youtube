Loaders and splitters

Part two of the RAG notes: the indexing machinery. What each piece does, what's underneath it, when the built-in one is enough, and how to decide between chunking strategies instead of guessing.

These two steps decide what can ever be retrieved. Anything a loader drops or a splitter cuts badly is invisible to the rest of the system — no reranker or bigger model recovers it.

Part one

Document loaders

A loader's job is narrow: take a source in whatever form it lives, and return a list of Document objects. Each one is just text plus a metadata dictionary.

Document(
    page_content = "Refunds are processed within 5–7 business days...",
    metadata = {"source": "policy.pdf", "page": 12}
)

That uniform output is the whole point. Everything downstream — splitter, embedder, vector store, retriever — only ever sees this shape, so adding a new source type never touches the rest of the pipeline.

The built-in ones and what's underneath

You noticed correctly that each loader wraps a different library. The loader itself is usually a thin adapter; the parsing quality comes from the library behind it.

PDFs are where projects stall

A PDF has no notion of paragraphs or reading order — only glyphs at coordinates. Every extractor is guessing. Before blaming retrieval, print the extracted text of a few pages and read it. Scrambled two-column text or vanished tables explain most "the RAG doesn't work" reports. Scanned PDFs have no text layer at all and need OCR (Tesseract, or a vision model) before anything else works.

Built-in or custom?

In practice, both. Start with the built-in and write a custom one when you hit a specific wall:

SituationApproach
Standard format, clean fileBuilt-in loader. No reason to write code.
Source has no loaderCustom — internal API, proprietary format, a database join.
Need richer metadataCustom. Section titles, doc owner, last-updated date, access level — none of it comes free.
Boilerplate pollutes chunksCustom, or subclass to strip headers, footers, nav, legal blocks before returning.
Structure must surviveCustom. Emit one Document per section rather than per page, so chunks align with meaning.

A custom loader is small — subclass the base and yield Documents:

from langchain_core.document_loaders import BaseLoader
from langchain_core.documents import Document

class TicketLoader(BaseLoader):
    def __init__(self, client, project):
        self.client, self.project = client, project

    def lazy_load(self):
        for t in self.client.fetch(self.project):
            yield Document(
                page_content=f"{t.title}\n\n{t.description}\n\n{t.resolution}",
                metadata={
                    "source": t.url,
                    "ticket_id": t.id,
                    "status": t.status,
                    "updated": t.updated_at,
                },
            )
Metadata is the cheapest win in the pipeline

It costs nothing at load time and pays off three ways: filtered retrieval ("only current-version docs"), citations in the answer, and targeted deletion when a document is withdrawn. Retrofitting it later means re-indexing everything.

Part two

Text splitters

Splitting exists because of a squeeze from both sides. Chunks that are too large dilute the embedding — one vector has to represent several topics, so it matches nothing sharply. Chunks that are too small carry no context, so the retrieved fragment is true but useless.

The strategies, in order of how much machinery they need

1. Fixed-size

Cut every N characters or tokens. Structure-blind, so it happily slices mid-sentence, but it's fast, predictable and a legitimate baseline. Research keeps finding it harder to beat than people expect.

2. Recursive character splitting

The default workhorse, and worth understanding properly rather than treating as a black box. It holds an ordered list of separators — by default ["\n\n", "\n", " ", ""] — and works down it:

  1. Try splitting on paragraph breaks. If every resulting piece fits the size limit, done.
  2. Any piece still too large gets split again on single newlines.
  3. Still too large — split on spaces, then on raw characters as the last resort.

The effect is that it breaks at the largest natural boundary that satisfies the size constraint, and only resorts to brutal cuts where the text gives it nothing to work with. That's why it's the sensible default for prose.

3. Token-based

Same idea, but counting tokens via tiktoken instead of characters. Matters because your size limits are really token limits — character counts drift badly across languages, code, and text with many numbers.

4. Structure-aware

Split along the document's own skeleton instead of guessing at it: Markdown headers, HTML tags, or language-aware separators for code (splitting at function and class boundaries rather than mid-body). When the structure exists, using it beats inferring it — and header text can be copied into each chunk's metadata, so a chunk knows which section it came from.

5. Semantic

Exactly as described in the tutorial: split into sentences, embed each one, walk through comparing adjacent similarity, and cut where similarity drops — a drop implies the topic changed. Intuitive and appealing.

The evidence is more mixed than the intuition suggests. Chroma's chunking study found strategy choice matters a lot (up to around nine points of recall between strategies), but that heuristic splitters like recursive remain strong baselines. A NAACL 2025 paper tested semantic chunking across document retrieval, evidence retrieval and answer generation and concluded the gains over simple fixed-size chunking were inconsistent and didn't justify the compute. So: reasonable to try, not something to adopt on faith.

6. LLM-based

Ask a model where the natural boundaries are. Best quality in some evaluations, and the most expensive by a wide margin — every document costs a generation pass. Viable for small, high-value, stable corpora; rarely viable at scale.

Overlap, across all of them

Repeat some tail of each chunk at the start of the next, so a sentence spanning a boundary survives in at least one chunk intact. Ten to twenty percent of chunk size is the usual range. It costs storage and adds redundancy in results, so more is not better.

How to decide

The honest answer is that you measure. But you can narrow the search space a lot before measuring anything:

What you're indexingStart withBecause
Prose — articles, reports, policiesRecursive, 500–800 tokens, 10–15% overlapParagraph boundaries are meaningful and the separator cascade respects them.
Markdown, wikis, docs sitesHeader-based, then recursive inside long sectionsThe heading hierarchy is a better outline than anything you'd infer.
CodeLanguage-aware splitterA function cut in half retrieves as nonsense.
FAQs, tickets, product recordsOne chunk per record, no splittingThe record is already the unit of meaning. Don't fight it.
Tables and spreadsheetsRow groups plus the header row repeatedA detached row loses its column names and means nothing.
Transcripts, chat logsTime or speaker windows with generous overlapTopics drift gradually and references point backwards.
Legal, contractsClause or section boundariesClauses are self-contained by design and get cited individually.

The procedure

  1. Build a small eval set first. Thirty to fifty real questions, each labelled with the passage that answers it. Everything after this is guesswork without it.
  2. Measure retrieval alone. Recall@k — does the right passage come back in the top k? Keep the generator out of it, or you can't tell which stage failed.
  3. Sweep chunk size and overlap on the simplest splitter that fits your document type. This is usually the biggest single lever.
  4. Only then try fancier strategies, and only if the simple one is demonstrably losing. Compare against the same eval set and count the compute cost.
  5. Re-check when the corpus changes. A setting tuned on clean docs degrades when someone dumps in scanned PDFs.
The order that saves time

Fix extraction quality first, then chunk size, then retrieval settings (k, hybrid search, reranking), then chunking strategy. Most people start at the last one because it's the most interesting, and spend a week tuning a semantic splitter on text the loader mangled.

Beyond plain chunking

Once the basics are measured, these are the techniques that show up when a plain split isn't enough. Each one addresses the same root problem: a chunk pulled out of its document has lost the context that made it meaningful.

  • Contextual retrieval — prepend a short model-generated blurb to each chunk explaining where it sits in the document, then embed that. Attacks the context-loss problem head-on at the cost of one generation pass per chunk.
  • Late chunking — embed the whole long document first, then pool per chunk afterwards, so every chunk vector carries surrounding context. Needs a long-context embedding model, but requires no extra training.
  • Small-to-big / parent document — retrieve on small precise chunks, then hand the model the larger parent section they came from. Cheap and often the single best upgrade.
  • Hierarchical summarisation — build a tree of recursive summaries above the raw chunks so broad questions can be answered from a higher level. RAPTOR is the reference implementation.
  • Hybrid search plus reranking — combine dense vectors with keyword search, then rerank with a cross-encoder. Frequently beats any amount of chunking tuning, especially for exact terms, IDs and error codes.
Part three

Papers and reports

Ordered so the chunking-specific ones come first, since that's the open question here.

  • Evaluating Chunking Strategies for Retrieval Smith & Troynikov, Chroma technical report, 2024 Evaluates popular strategies at token-level precision and recall. Finds strategy choice materially affects retrieval, while heuristic splitters like recursive stay competitive. Comes with a runnable evaluation package — the most directly useful item on this list. research.trychroma.com/evaluating-chunking
  • Is Semantic Chunking Worth the Computational Cost? Qu, Tu & Bao — Findings of NAACL 2025 (arXiv 2410.13070) Tests semantic chunking against fixed-size across three retrieval tasks and finds the gains inconsistent and not worth the compute. The direct counterweight to the intuition that semantic splitting must be better. arxiv.org/abs/2410.13070
  • Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models Günther et al., Jina AI, 2024 (arXiv 2409.04701) Flips the order — embed the full text, chunk afterwards at the pooling step — so each chunk vector retains document context. No retraining needed. arxiv.org/abs/2409.04701
  • Searching for Best Practices in Retrieval-Augmented Generation Wang et al., EMNLP 2024 (arXiv 2407.01219) Sweeps the whole pipeline — chunking, embeddings, retrieval, reranking, generation — looking for combinations that balance quality against cost. Useful as a map of which knobs actually move results. arxiv.org/abs/2407.01219
  • Introducing Contextual Retrieval Anthropic engineering writeup, 2024 The contextual-embeddings technique in practical form, with reported failure-rate reductions when combined with hybrid search and reranking. anthropic.com/news/contextual-retrieval
  • RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval Sarthi et al., ICLR 2024 (arXiv 2401.18059) Builds a summary tree over the corpus so retrieval can happen at several levels of abstraction. The answer to "my questions need the whole document, not a chunk". arxiv.org/abs/2401.18059
  • Lost in the Middle: How Language Models Use Long Contexts Liu et al., TACL 2024 (arXiv 2307.03172) Models attend well to the start and end of a long context and poorly to the middle. Explains why retrieving fewer, better chunks beats retrieving more, and why the order you paste them in matters. arxiv.org/abs/2307.03172
  • Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks Lewis et al., NeurIPS 2020 (arXiv 2005.11401) The original paper that named the pattern. Worth reading once for the framing, though the architecture it describes is not what people build today. arxiv.org/abs/2005.11401

If you only act on one thing here: build the labelled question set before touching splitter settings. Every decision downstream becomes measurable, and most of them stop being arguments.
