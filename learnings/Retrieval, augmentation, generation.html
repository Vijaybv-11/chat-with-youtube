Retrieval, augmentation, generation

Part four of the RAG notes: everything that happens after a question arrives. The indexing half decides what can be found; this half decides what actually gets found, what reaches the model, and what it does with it.

Almost every disappointing RAG answer is created here. The model is rarely the problem — the shortlist it was handed usually is, and the only way to know is to inspect the two separately.

Part one

Retrieval

The retriever takes a question and returns chunks. That's the whole interface, and the reason it's deceptive: the interface never changes while the quality of what comes back varies enormously.

Top-k, and the trap inside it

k is how many chunks you take. Too few and the answer isn't in the context. Too many and you dilute the prompt, burn tokens, and push the useful chunk into the middle where models attend least.

Three to five is the usual starting range with reranking, five to ten without. But the number matters less than this:

Similarity search always returns something

Ask your YouTube bot about the offside rule and it will still return the five chunks nearest that question — nearest in a corpus where nothing is close. The scores will be poor, but a plain top-k retriever doesn't look at scores, it looks at rank. The model then gets five irrelevant chunks and an instruction to answer, and often obliges.

Fix: set a similarity threshold and return nothing below it, then handle the empty case explicitly in the prompt. This is the single most common missing piece in first builds, and the reason "ask it something not in the video" is such a good test.

MMR — when results are redundant

Pure similarity often returns five near-identical chunks, especially with overlap. Maximal marginal relevance re-scores candidates by relevance minus similarity to what's already selected, so the set covers more ground. Useful for broad questions; unnecessary for narrow factual ones.

Metadata filtering

Restrict the search before or during similarity: current version only, this product only, documents this user may see. This is also where permissions live — and worth repeating that filtering interacts awkwardly with approximate indexes, so test that a heavily filtered query still returns good results rather than whatever survived.

Hybrid search

Dense vectors are good at meaning and bad at exact strings. Ask about error code E4017 or a surname, and embeddings will cheerfully return chunks about similar-sounding things, because nothing in the geometry makes an exact token match special.

Keyword search (BM25) is the opposite — excellent at exact terms, useless when the user's wording differs from the document's. Hybrid runs both and fuses the ranked lists, usually with reciprocal rank fusion, which merges by rank position so the two score scales never have to be reconciled.

For most real corpora this is a bigger win than any amount of chunking tuning, because real questions contain names, IDs, version numbers and error codes.

Query transformation

The user's question is often a bad search query. Four fixes, in rough order of how often you need them:

TechniqueWhat it doesWhen
History rewritingTurns "what about the second one?" into a standalone question using the conversation so far.Mandatory for any chatbot. Follow-ups are unretrievable as written.
Multi-queryGenerates several phrasings, retrieves for each, merges.Vague or short questions.
DecompositionSplits a compound question into sub-questions, retrieves per part.Multi-hop: "how does X compare to Y?"
HyDEHas the model write a hypothetical answer, embeds that, and searches with it.When questions and documents are written in very different registers.
For your YouTube bot specifically

History rewriting is the one that matters. In a transcript corpus, a follow-up like "why did he say that?" embeds to nothing useful — the pronouns carry all the meaning and none of it is in the text. Rewrite before retrieval, not after.

Small-to-big retrieval

Match on small chunks for precision, then send the model the larger parent section those chunks came from. You get sharp retrieval and intact context at the same time. For transcripts this works unusually well: match on a tight window, expand to the surrounding two minutes.

Part two

Augmentation

No model runs here. It's string assembly — which is why it gets skipped in tutorials and why it's one of the better places to spend an afternoon.

The structure of the prompt

[1] Role and grounding rule
    "Answer using only the context below. If the context does not
     contain the answer, say you don't know. Cite the chunk id
     for each claim."

[2] Context block, delimited, each chunk labelled
    <context>
    [id: t_0412 | 12:30–13:10] ...chunk text...
    [id: t_0417 | 14:02–14:48] ...chunk text...
    </context>

[3] Conversation history, if any (trimmed)

[4] The question

[5] Output instructions — format, length, what to do when unsure

Things that actually change results

  • Order. Models attend best to the start and end of a long context and worst to the middle. With several chunks, put the strongest at the top and the second strongest at the bottom. Free to implement, measurably helps.
  • Labelling. Give each chunk an id and its source metadata. Without ids the model cannot cite, and you cannot verify citations afterwards.
  • Delimiters. Clear boundaries stop the model from reading two unrelated chunks as one continuous passage, which produces confident nonsense.
  • Deduplication. Chunk overlap means adjacent chunks share text. Strip repeats before assembling or you pay tokens twice and bias the model toward the duplicated part.
  • The refusal clause. Without an explicit instruction to say "I don't know", the model falls back on its own training knowledge the moment retrieval comes up short — and you cannot tell from the output that it did.

The token budget

A large context window is not permission to fill it. Cost scales with tokens on every call, latency scales with them, and accuracy degrades once the useful content is buried. Budget deliberately: reserve room for the system prompt, history and the answer, and give context whatever's left — not the other way round.

Retrieved text is untrusted input

Anything that reached your index can reach your prompt. A document containing "ignore previous instructions and ..." is an injection vector, and in a YouTube bot that document is a transcript of whatever someone chose to say on camera. Treat retrieved content as data: keep it inside clear delimiters, state in the system prompt that context is reference material and never instructions, and never let retrieved text decide an action your app will take. This is a real attack surface, not a theoretical one.

Part three

Generation

The smallest stage, and the one people over-tune. If retrieval and assembly are right, generation is mostly unremarkable.

Settings

  • Temperature low — near zero for grounded question answering. You want faithful reading, not creative writing.
  • Model size — a smaller model with excellent context usually beats a larger one with poor context, at a fraction of the cost. Upgrade the retriever before upgrading the model.
  • Streaming — doesn't improve answers, dramatically improves perceived latency when the retrieval stack has added half a second.

Citations

Ask for chunk ids inline, then map them back to sources in your code. Don't let the model write URLs or titles from memory — it will invent plausible ones. If citation accuracy matters, verify afterwards: check that each cited id was actually in the context you sent, and optionally that the claim is supported by that chunk.

How generation fails even with good context

  • Parametric leakage — answers from training knowledge instead of the context. Detectable by feeding deliberately wrong context and seeing whether the answer changes.
  • Blending — mixes context with prior knowledge into one seamless paragraph, so part of it is grounded and part isn't, with no visible seam.
  • Over-refusal — the answer is right there in the context and it still says it doesn't know. Usually an over-strict grounding instruction.
  • Fabricated citations — cites ids that weren't in the context at all.

The practical payoff of separating the stages. When an answer is bad, don't tune — find the stage first.

Part five

What to measure at each stage

Stage-separated metrics are the only way the triage table above stops being guesswork. End-to-end scores tell you something broke; these tell you where.

StageMetricQuestion it answers
RetrievalRecall@kIs the answer-bearing chunk in the top k at all? The ceiling on everything downstream.
RetrievalPrecision@k / context precisionHow much of what you retrieved was actually useful? Low precision wastes tokens and buries the good chunk.
RetrievalMRR or NDCGHow high up is the good chunk? Matters because of position effects.
GenerationFaithfulness / groundednessIs every claim supported by the supplied context?
GenerationAnswer relevanceDoes it address the question, or something adjacent that got retrieved?
End to endRefusal accuracyDoes it decline when it should, and only when it should? Needs deliberately unanswerable questions in the set.
End to endCitation correctnessDo cited ids exist in the context, and support the claim?

RAGAS and DeepEval implement most of these out of the box. Both lean on an LLM as judge for faithfulness and relevance, which means the judge itself needs checking against human labels before you trust its numbers — a judge that scores everything 0.9 tells you nothing.

The one habit worth forming now

Keep a fixed set of questions with known answers and known source passages, and run it after every change. Thirty is enough to start. Without it, "I tweaked the chunk size and it feels better" is the entire quality process — and feelings don't catch regressions in the cases you didn't happen to try.
